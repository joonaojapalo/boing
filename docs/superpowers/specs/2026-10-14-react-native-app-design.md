# Boing native app (React Native) — design

Date: 2026-10-14. Asked for overnight ("make the React Native implementation"); decisions below were
taken without a review round and are open to change.

## Why

The phone browser delivers 30 fps. Flight-time error per frame of timing error is ≈ 3.5 cm at 30 fps,
1.8 cm at 60, 0.9 cm at 120, 0.45 cm at 240. A native app can record at the camera's highest frame rate.

## Shape

- `mobile/`: Expo app (continuous native generation: `android/` and `ios/` are generated by
  `expo prebuild` and not committed). Expo gives file system, speech, keep-awake, document picker, and
  EAS Build for iOS without a local Xcode.
- Camera: **VisionCamera 5** (Nitro). One session with three outputs: preview, video (recording), frame
  output (live pose). Constraint `{ fps: max }` where `max` is the device's highest supported fps (capped
  at 240). The selected fps is shown on screen.
  - iOS formats include 120/240 fps (slow-motion formats) on most iPhones.
  - Android: VisionCamera uses CameraX regular sessions; expect 30 or 60 fps. Constrained high-speed
    sessions (120/240) are not reachable through it. Slow-motion files from the phone's own camera app
    can still be imported and analysed at their full capture rate.
- Pose: **MediaPipe Pose Landmarker** (same models as the web app: lite/full/heavy `.task` files,
  downloaded on first use and cached), in a local Nitro module `mobile/modules/boing-pose`:
  - `PoseDetector.detect(frame)` — synchronous, called from the frame-output worklet; returns the frame
    time in seconds and 33 landmarks (x, y, z, visibility) or none.
  - `PoseDetector.analyzeVideo(path, from, to, onProgress)` — decodes a video file frame by frame
    (Android: MediaExtractor sample times + MediaMetadataRetriever frames; iOS: AVAssetReader) and runs
    VIDEO-mode detection on **every** frame in the window, with each frame's own presentation time.
  - `videoInfo(path)` — size, duration, frame count, average fps, capture fps (Android slow-motion
    metadata), rotation.
- Analysis: the existing `src/analysis/` (pure TypeScript) is shared unchanged via Metro `watchFolders`;
  `findJumps`, `toSignals`, `JumpTracker` run in JS on landmark arrays.

## Live flow (same idea as the web app's continuous recording)

1. Start: camera session runs; recorder starts writing a clip; frame output runs pose on as many frames
   as the phone manages (`dropFramesWhileBusy`), feeding `JumpTracker` and the setup status
   ("Feet not visible · step back", "Ready", …).
2. A live jump is reported → "Measuring…". Shortly after landing the clip is stopped and a new clip
   starts at once. The finished clip is analysed around the jump on every recorded frame
   (`analyzeVideo`), `findJumps` runs on it, and the jump closest to the live takeoff (±0.5 s) wins.
   Live↔clip time mapping: the live frame time when the recording started (approximate; the window is
   padded and matched, as on the web).
3. If refinement fails, the live result is shown with "≈" (same rules as the web app).
4. Clips without a jump are rotated every ~20 s and deleted, so storage stays small.

## Import flow

Pick a video (document picker) → `videoInfo` → `analyzeVideo` over the whole file (heavy model) →
time scale for Android slow-motion files (`capture fps / playback fps`) → `findJumps` → results.

## UI

Single screen like the web app: camera/video area, status pill, big latest height ("≈" when
approximate), session row (count, best, average, chips), detail sheet (height, flight-time height, time in
the air, fps, frames in the air, plot of hips/toes), buttons: import, start/stop, flip camera, sound.
Spoken result (expo-speech) + haptic. Screen kept awake while live.
Only setup instructions are ever shown; never anything about jump technique.

## Verification available tonight

- No Xcode on this Mac: the iOS code is written but **not compiled**. EAS Build (cloud) or installing
  Xcode is needed.
- Android: JDK 17 + Android SDK installed via Homebrew; debug APK built locally; run on an arm64
  emulator. A debug-only deep link analyses a pushed test video and logs the jumps, compared with the
  web pipeline's results for the same video.
- Pure TS logic (fps choice, clip/time mapping, session summary) unit-tested with Vitest.
